## 1. Fixed in this pass ✅ (each behind a regression test)

### [HIGH] League-format tournaments never completed — no champion, prizes, or circuit points
- **Files:** `engine/processors/tournament-completion.ts:44`, `engine/tournament-manager.ts:872` (`calculatePlacements`), `engine/tournament/league-schedule.ts:87` → `bracket-scheduling.ts:17`.
- **Root cause:** `setupLeagueSchedule` stores every round-robin match in `tournament.playoffBracket` (via `addBracketMatch`). `hasTerminalTournamentCompletion` therefore always took the **bracket** branch, searched for a terminal "final"/"grand final" stage (a league only has `"League Match"` stages), found none, and returned `false` forever. The dedicated `format === "league"` branch was **unreachable dead code**. Every `"league"` calendar event (6 in `data/tournaments.json` — EPL/ESL Pro League, Challenger, ESEA Premier, etc.) hung indefinitely: no champion locked, **$0 of their prize pools paid**, no circuit points, no trophies, leaderboards never updated.
- **Second latent bug found while fixing:** the league branch's pending-match check filtered `m.week <= currentWeek`, but a round-robin schedules every match up front — so once week 1's matches were played while later weeks remained, it would have completed the league **prematurely** (after one week). The existing unit test even encoded this (`"future match doesn't block completion" → true`), but only passed because the branch was dead.
- **Third bug:** `calculatePlacements` had no league path — it would only place teams with `losses >= 3` (the Swiss-fallback branch) at positions 9+, so the **champion was never placed at position 1** and the 40% first-place prize/points went to nobody.
- **Fix:** (a) run the league branch *before* the bracket branch in `hasTerminalTournamentCompletion`; (b) complete a league only when **no scheduled matches remain** for it; (c) add a league branch to `calculatePlacements` that ranks by the (engine-sorted) `standings`. The champion = `standings[0]`, prizes/points distribute by standings order.
- **Tests:** `tournament-integrity.test.ts` ("League completion …" — does-not-complete-early, completes-and-crowns-leader, no-double-award) + corrected `tournament-completion.test.ts` league-path tests.

### [MEDIUM] Swiss rounds granted multiple BYEs → wrong teams qualified
- **File:** `engine/tournament/swiss-handlers.ts:80` (`generateSwissRound`).
- **Root cause:** the odd-one-out in **every** W-L bucket got a free win, so a round with N odd-sized buckets handed out N BYEs. Real Swiss grants at most one BYE per round. Because qualification is "advance at **exactly** 3 wins", surplus BYEs pushed the wrong teams over the threshold and corrupted who reached the playoff bracket. (Reachable in normal 16-team Swiss whenever ≥2 buckets are odd-sized — common.)
- **Fix:** defer each bucket's odd team into a `leftovers` list, **float-pair** them across adjacent buckets (strongest-first, deterministic tiebreak), and grant a single BYE only to the final unpaired (weakest) team — so at most one BYE per round.
- **Bonus (deadlock guard):** if a generated round schedules zero real matches (≤1 active team → only a BYE), nothing would ever call `handleSwissResult` to advance it. Added a guard in `handleSwissResult` that jumps straight to playoffs in that case.
- **Tests:** new `swiss-pairing.test.ts` (zero byes when leftovers cross-pair, exactly one legitimate BYE for a single odd bucket, one-BYE cap with three odd buckets, no double-booking / self-match).

### [MEDIUM] `processFinance` was the only week-step missing replay/resume dedup
- **File:** `engine/processors/finance-processor.ts:13`; call site `engine/atomic-week-processor.ts:248`.
- **Root cause:** every other week-processor step threads an `eventIdSet`/`ledgerIdSet` and guards its pushes; `processFinance` did not — it pushed `exp_wage_*`, `inc_*`, `exp_fac_`, `exp_equip_`, and the budget-warning event with no existence check. Harmless only because the current resume model re-runs a whole tick from the last *persisted* save; the moment any replay fed a week onto an already-mutated save, wages would double-charge and ledger IDs duplicate (breaking `integrity-checker` reconciliation).
- **Fix:** thread `eventIdSet`/`ledgerIdSet` into `processFinance`, guard every ledger and event push (with an internal fallback set so it's still correct when called without args). The single-run path is unchanged (IDs are fresh).
- **Tests:** `finance-processor.test.ts` — re-running a week adds no duplicate ledger entries (threaded + fallback) and re-emits no budget warning.

### [MEDIUM] `saveGame()` was not serialized → concurrent writes could race the save protocol
- **File:** `store/game-store.ts` (`saveGame` action + module-level `saveChain`).
- **Root cause:** the post-tick authoritative save, the 60 s autosave, and any rapid manual save could overlap and interleave `SaveManager`'s tmp-stage → commit → backup-rotation on the same key (the `isLoading` guard is already `false` during the brief post-tick reveal+save phase).
- **Fix:** serialize `saveGame()` through a race-free promise chain — concurrent callers queue in invocation order and each runs on the freshest state; the chain swallows prior rejections so one failed save can't wedge the next, while each caller still receives its own result/rejection.

### [LOW] `legendaryPlayers` pushed without a dedup guard
- **File:** `engine/atomic-week-processor.ts:379,388`.
- **Root cause:** a legend surfacing from both the retirement and mid-season-retirement passes in the same tick pushed two heavy full-player clones; the array is in no `ARRAY_CAPS`/prune path.
- **Fix:** guard both pushes by `player.id`, bounding the array to the finite legend population.

### [LOW] FPL match IDs embedded `Date.now()` → non-deterministic persisted saves
- **File:** `engine/fpl-engine.ts:502`.
- **Root cause:** the FPL match record (persisted in `fplData.matchHistory`) used `fpl_match_${week}_${Date.now()}_${rng.int(...)}`. Two games with the same seed produced divergent save contents, undermining save-hash reproducibility. The `rng` draw already provides deterministic, collision-resistant uniqueness.
- **Fix:** drop `Date.now()`; use `fpl_match_${week}_${rng.int(0, 0x7fffffff).toString(36)}`.

### [LOW] Misleading "live" comment on the dead circuit-points awarder
- **File:** `engine/processors/circuit-points-awarder.ts` header.
- **Root cause:** `awardCircuitPoints` has zero production callers (`standings-processor` is the sole, idempotent awarder since the integrity pass), but its comment claimed "Called from processTournaments…" — luring a maintainer into re-wiring a **double-awarder**.
- **Fix:** marked it clearly as DEAD with a do-not-re-wire warning (kept because `circuit-points-awarder.test.ts` documents the placement/trophy-dedup rules).

## 2. Verified-open findings — documented, not auto-fixed

These are real and traced, but each is either a behaviour-changing determinism
refactor (prior passes deferred these deliberately, pending dedicated coverage)
or carries unvalidated risk. Recorded here with precise remediation.

### [HIGH risk / MEDIUM value] Mid-tick `save.lastRngSeed` re-seeding leaks pre-tick + finance RNG into Swiss pairings
- **Files:** `finance-processor.ts:19,222`; `swiss-handlers.ts:208`; `standings-processor.ts:329`.
- **What:** `processFinance` re-seeds from `save.lastRngSeed` and **writes it back** mid-tick; later, Swiss next-round pairing (`generateSwissRound`'s `new SeededRNG((save.lastRngSeed ?? 1) + roundNum)`) and the legend-pick shuffle read that mutated value. So the pre-tick event count (each `nextDeterministicId` advances `lastRngSeed`) and the finance-news RNG perturb **competitive** Swiss bracket pairings — not just cosmetics.
- **Fix (sizeable):** thread the single tick `rng` into `processFinance`, the Swiss handlers, and `queueLegendPick`; stop re-seeding from `save.lastRngSeed` mid-tick; let only the final week-processor step write `save.lastRngSeed`. Pin with a "two identical saves → identical Swiss pairings regardless of pre-tick event count" test before landing.

### [MEDIUM] `nextDeterministicId` embeds an RNG draw (Phase 4.1, still open)
- **Files:** `store/utils/helpers.ts:33`, duplicated at `store/game-store.ts:123`.
- **What:** despite the name, the ID consumes `nextRandomInt`, advancing `lastRngSeed`. Pre-tick mutations (level-ups, weekly/scheduled activities, auto-registration) thus perturb the stream the above consumers read, and IDs aren't idempotent on replay. **The 50+ call sites mean content-addressing requires a unique stable key per site** — a wide, risky change. Recommend doing it together with the H1 fix above, behind tests.

### [MEDIUM] `"swiss"` events with non-16/24 fields silently run as single-elimination
- **File:** `engine/tournament-manager.ts:277-292` routes by participant **count**, ignoring `tournament.format`. `data/tournaments.json`'s 8-slot `copenhagen_rmr_asia` / `shanghai_rmr_asia` are declared `"swiss"` but run as a bracket (one loss eliminates, vs. Swiss's 3).
- **Why not auto-fixed:** routing them to Swiss exercises an **8-team Swiss + top-8 playoff** path that the prior 200-seed verification (16-team only) never covered; small-field playoff sizing (`SWISS_PLAYOFF_BRACKET_SIZE = 8`) is unvalidated. **Fix:** route on `tournament.format === "swiss"` for even fields ≥ a minimum, then add a small-field Swiss end-to-end test before shipping.

### [LOW] Dead "loaded-gun" save paths
- `saveGameCheckpoint` (`save-manager.ts:413`): only a test caller; rewrites `updatedAt` without recomputing `integrityHash`, so re-wiring it would fail `verifyIntegrityHash` on load.
- `rollbackTransaction` (`save-manager.ts:999`) reachable only via `AtomicWeekProcessor.rollback` (`atomic-week-processor.ts:548`), which has **zero callers**; it restores from a bare backup key `saveGame` no longer writes.
- **Fix:** delete both (and `AtomicWeekProcessor.rollback`), or repair the hash/backup-key — they're recovery scaffolding, so confirm intent first.

### [LOW] `circuitPoints[].results[]` grows unbounded across seasons
- **File:** `tournament-qualification.ts:128` — `applySeasonalDecay` keeps full history. **Caution:** `results` feeds the ranking tiebreaker (major-win count + latest week at `:110-116`), so a cap must preserve the major-win count — recommend a generous cap (e.g. last 100) rather than a tight trim.

### [LOW, dev-only] `IntegrityChecker` ledger reconciliation false-positives
- **File:** `integrity-checker.ts:123-142` assumes each ledger entry's `balance = prev + amount·sign`, but `finance-processor` writes a week's player-team entries with the same final `team.budget` while amounts differ. Only invoked from the dev panel (`app/dev/page.tsx`), so it's spurious dev noise, not a player-facing bug. Reconcile per-week-net instead of per-entry.
